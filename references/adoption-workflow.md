## 收集依赖证据

按可信度从高到低收集：

1. 当前模块的 `pom.xml`、`build.gradle`、`build.gradle.kts` 或版本目录。
2. 父 POM、BOM、Gradle platform、version catalog 和项目属性中的实际版本。
3. 当前源码已有的 Hutool import 与统一封装。
4. 已解析依赖、本地 JAR、源码包或 Javadoc。
5. 锁文件、CI 配置或构建日志中的解析结果。

区分以下概念：

- `dependencyManagement`、BOM 或 version catalog 只管理版本，不代表模块已经进入编译/运行依赖。
- 父模块声明不一定对当前子模块可见，检查 scope、configuration 和 excludes。
- 传递依赖可能在升级后消失；需要直接使用的模块应服从项目依赖规范。
- `hutool-all` 是聚合依赖；单模块项目不能因为存在 `hutool-core` 就使用 HTTP、JSON、POI 或 JWT。

## 决定能否使用

| 当前状态 | 操作 |
|---|---|
| 已有兼容模块和可核实 API | 直接使用，保持现有版本 |
| 已有同版本 `hutool-all` | 核实该版本确实包含目标模块后使用 |
| 只有 `hutool-core`，目标属于其他模块 | 不假定可用；先判断任务是否允许修改构建文件 |
| 允许新增依赖 | 增加与现有 Hutool 完全同版本的最小模块，并检查可选第三方依赖 |
| 不允许或未授权新增依赖 | 保留当前实现或使用现有 JDK/框架方案，并说明 Hutool 候选 |
| 版本无法确认 | 不生成未经核实的精确 API；继续查证或明确缺少的信息 |
| 项目已有统一封装 | 优先通过封装使用，不绕过鉴权、序列化、事务、审计或生命周期 |

不要为了使用一个方法把单模块依赖改成 `hutool-all`，也不要顺手升级 Hutool 主版本。

## 主动发现候选

编写或审查 Java/Kotlin 代码时主动识别下列信号：

| 代码信号 | 优先检索 |
|---|---|
| 重复的 null、空白、前后缀、模板拼接 | `StrUtil`、`ObjectUtil` |
| 集合判空、交并差、分组、分页 | `CollUtil`、`ListUtil`、`MapUtil` |
| Bean/Map 转换、字段复制、类型转换 | `BeanUtil`、`CopyOptions`、`Convert` |
| 日期解析、偏移、区间、格式化 | `DateUtil`、`DateTime`、`DateRange` |
| 文件读写、流复制、资源加载 | `FileUtil`、`IoUtil`、`ResourceUtil` |
| UUID、雪花 ID、随机值 | `IdUtil`、`RandomUtil`；安全随机另行处理 |
| URL、Hex、Base64、压缩、脱敏 | Core 对应 Util |
| JSON 对象/数组与 Bean 互转 | `hutool-json`、`JSONUtil` |
| 同步 HTTP、表单、上传下载 | `hutool-http`、`HttpRequest` |
| 摘要、HMAC、AES、RSA、国密 | `hutool-crypto`、`SecureUtil` |
| Excel 导入导出 | `hutool-poi`、`ExcelUtil` |
| 轻量 JDBC 操作 | `hutool-db`、`Db`、`Entity` |
| JWT 创建、解析和验证 | Hutool 5.x `hutool-jwt` |
| 邮件、二维码、拼音、模板、SSH 等 | `hutool-extra` 及相应可选引擎 |

只把这些信号当作检索入口。候选 API 必须比现有代码更清楚，并且保持行为与架构边界。

## 检查行为等价

替换前至少比较与任务相关的项目：

- null、空字符串、全空白字符串和空集合的行为；
- 默认字符集、大小写、Locale、时区和日期宽松解析；
- 数值溢出、金额精度、scale 与舍入模式；
- 异常类型、是否吞异常、默认值和失败返回值；
- 是否复制、是否修改入参、顺序、去重和线程安全；
- 资源所有权、自动关闭、懒加载和一次性流；
- 序列化字段、日期格式、枚举、泛型、未知字段和 null；
- 网络超时、重定向、代理、Cookie、TLS、重试和响应大小；
- 加密模式、填充、编码、密钥格式、随机源和互操作协议；
- 数据库连接、事务、方言、参数绑定和受影响行数。

任何一项无法保持时，不做无说明替换。必要时保留现有实现或使用项目封装。

## 核实 API

按以下顺序确认类与方法：

1. 当前项目已有、可工作的用法。
2. 当前版本本地 JAR、源码或 Javadoc。
3. 与精确版本匹配的 Hutool 官方 API 和源码分支。
4. 本 Skill 的 `data/` 文档只作为定位和常见用法参考。

核实类全名、所属 artifact、方法重载、参数顺序、返回类型、异常、最低版本和废弃状态。不能只凭另一个主版本中存在同名类就推导 API。

## 实施修改

- 做最小范围改动，不顺手迁移无关代码或升级依赖。
- 使用具体 import，移除确认无用的 import，不用通配符掩盖冲突。
- 不把 `JSONObject`、`Entity`、`DateTime` 等 Hutool 类型无故暴露到公共接口。
- 保持项目命名、格式、日志和异常处理风格。
- 需要新增依赖时说明 artifact、版本来源和可选第三方依赖。
- 安全敏感能力必须使用项目批准的算法与配置，不依赖便捷 API 的默认值。

## 快速验证与交付

若用户或仓库没有指定更强验证，默认执行快速验证：

1. 阅读修改后的相关代码和差异。
2. 检查括号、泛型、import、方法签名和明显类型问题。
3. 只运行已有且快速的语法/静态检查；不要自动执行全量构建、全部测试或与任务无关的命令。
4. 无法在不编译的情况下确认的类型或重载，明确标为未验证，不声称已经通过编译。

交付时说明：使用的模块和类、替换原因、依赖是否变化、完成的验证、未验证的运行行为。
